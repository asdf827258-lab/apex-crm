# CLAIMS & AFTERCARE EVIDENCE ENGINE

## 1. 왜 필요한가

업로드된 자료는 단순 홍보 이미지가 아니다.

- 실손에서 급여·비급여가 실제로 나뉘어 지급된 사례
- 하나의 수술에서 여러 정액 수술특약이 함께 지급된 사례
- 상해 보험금과 소액 특약 지급
- 고객이 미처 몰랐던 특정 진단보험금
- 납입면제로 남은 보험료 부담이 사라진 계약변경
- 고객의 자발적인 감사 메시지
- 설계사가 지급구조를 짧게 설명하는 실제 대화

이를 프로그램 안에서 **사후관리 실적 데이터베이스**로 바꾼다.

---

## 2. 사례 데이터 구조

- caseId
- 고객 익명 ID
- 담당 설계사
- 보험사
- 상품
- 사고·질병
- 청구일
- 지급일
- 총 지급액
- 지급 담보별 금액
- 미지급·삭감 항목
- 필요서류
- 심사기간
- 추가 보완
- 이의제기 여부
- 납입면제 여부
- 증거 이미지
- 지급명세서
- 고객 메시지
- 고객 활용동의
- 준법 승인
- 개인정보 검수
- 검증등급

검증등급:

- A: 보험사 지급명세서 + 증권/약관 + 고객동의
- B: 보험사 지급안내 + 고객동의
- C: 입금알림 + 지급사유 확인
- D: 고객 메시지 또는 상담 대화만 있음
- X: 검증되지 않아 외부 사용 금지

## 3. 사례의 상담 사용법

### 잘못된 사용

- “저 고객도 받았으니 고객님도 받습니다.”
- “이 보험은 무조건 지급됩니다.”
- 많은 금액만 모아 공포와 기대를 자극
- 고객정보가 남은 화면 공개
- 서로 다른 담보를 동일한 효과처럼 설명

### 올바른 사용

- “실제 지급 구조를 이해하기 위한 사례이며 고객님의 지급 여부는 약관과 사실관계에 따라 달라집니다.”
- 고객의 현재 담보와 같은 부분만 연결
- 어떤 서류와 지급요건이 작동했는지 설명
- 실손과 정액보험의 역할 구분
- 보험금뿐 아니라 납입면제와 사후관리도 재무성과로 표시

---

## 4. 상담 스토리 자동 생성

각 사례에서 다음 스토리를 생성한다.

1. 고객 상황
2. 발생한 사건
3. 어떤 서류를 준비했는지
4. 어떤 담보가 작동했는지
5. 총 지급액과 구성
6. 고객의 실제 부담과 남은 공백
7. 설계 시 배울 점
8. 사후관리에서 배울 점
9. 동일 결과 비보장 문구

---

## 5. 청구 관리 기능

- 청구 접수
- 서류 체크리스트
- 보험사별 진행상태
- 보완요청
- 예상 지급이 아닌 `청구 가능 담보 후보`
- 실제 지급
- 부지급 사유
- 이의제기 검토
- 고객 안내문
- 사후 만족도
- 사례화 동의

AI는 지급액을 확정하지 않는다. 약관과 보험사 심사가 최종이다.
